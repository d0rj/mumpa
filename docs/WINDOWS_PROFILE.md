# Единый Windows-профиль — 1.2.21

Windows теперь хранит медиатеку в `%USERPROFILE%\.mumpa`, независимо от
расположения EXE, версии сборки и того, кто запустил приложение. Android
сохраняет прежнее приватное хранилище приложения.

## Причина и диагностика

Раньше путь строился через `getApplicationSupportDirectory()` и AppData.
Windows может перенаправить AppData в `Packages/<host>/LocalCache/Roaming`
для процесса, запущенного из MSIX-хоста. При диагностике из Codex
`GetFinalPathNameByHandle` подтвердил такое перенаправление для библиотечного
JSON. Поэтому чтение привычного пути установочным скриптом не доказывает,
какой физический файл использует процесс, запущенный другим способом.
[Описание виртуализации Microsoft](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes).

Путь в домашней папке проверен отдельным файловым probe: он не перенаправлялся.
Он не зависит от ресурсов CompanyName/ProductName и не находится в папке
установки, проекта или кешей сборки. Новый EXE принимает диагностический
аргумент `--profile-report=<путь к новому JSON>`: после загрузки записывает
собственный физический путь, PID и количества треков/избранного/офлайн.
Ключи, cookies и пароли в этот отчёт не попадают.

## Однократный перенос

`ApplicationProfile` ищет только старые папки Mumpa: прежний support-путь,
пользовательский Roaming и тот же точный относительный путь Mumpa в
`LocalCache/Roaming` установленных пакетов Windows. Остальные данные этих
пакетов не читаются.

Из валидных снимков объединяются известные треки, плейлисты и избранное.
Конфликтующие настройки/метаданные берутся из профиля с большим числом
любимых и известных треков. Офлайн-аудио и собственные локальные файлы внутри
старого профиля копируются с SHA-256-проверкой, пути в JSON меняются на новые.
Различные файлы с одинаковым именем получают отдельный путь `imports/`.
Внешняя пользовательская музыка остаётся в исходных папках. Метаданные
торрентов, обложки и настройки аккаунтов сохраняются; исполняемые runtime,
движок и восстанавливаемый кеш не копируются.

Исходные профили не удаляются. Снимки до объединения хранятся также в
`.mumpa/backups/imported/`; они содержат приватные настройки и не должны
публиковаться. Основной JSON фиксируется после проверки копий. Если старые
данные существуют, но не читаются, запуск не подменяет их пустой медиатекой.

После первого переноса старые лайки повторно не импортируются, поэтому
последующее снятие сердечка сохраняется. Обычные `.bak` и дневные копии
продолжают работать. Межпроцессная блокировка `profile.lock` запрещает двум
экземплярам Mumpa одновременно перезаписывать один профиль; освобождается
после сохранения при выходе и автоматически ОС при завершении процесса.

## Проверка обновления

Установить обычный release с `--target lib/main.dart`, закрыв старое приложение
штатно. Запустить с отчётом из установочной среды, затем завершить и запустить
из Explorer/обычного процесса Windows с другим новым файлом отчёта. Оба
отчёта должны показывать один `.mumpa` и одинаковое избранное; сохранённая
офлайн-копия должна воспроизводиться после повторного запуска.

Проверки переноса, виртуализированных сериализованных путей, блокировки,
сохранности исходников и отказа при повреждении: `test/application_profile_test.dart`.
